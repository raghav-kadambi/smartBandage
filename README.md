# WoundSense — Smart Wound-Care Bandage demo (50% review build)

A small full-stack demo for the capstone: login, a live sensor-slider dashboard that runs a
real trained ML model, and a patient chat page that answers questions using the sensor context
(OpenRouter-backed, RAG to be added later per your PPT plan).

## What's actually implemented here

- **Auth**: Flask session login/signup, SQLite (`wound_bandage.db`, created automatically),
  passwords hashed with Werkzeug — no third-party auth service.
- **ML model**: `models/train_model.py` trains a `RandomForestClassifier` (condition:
  healthy / wound_healing / infected) and a `RandomForestRegressor` (estimated days to heal)
  on your 5 sensor features.
- **Dashboard**: 5 sliders (pH, temperature, humidity, exudate level, oxygen saturation) that
  call `/api/predict` live and show the predicted condition, confidence, class probabilities,
  and estimated healing days.
- **Patient chat**: a bottom chat bar that sends your question + your latest sensor reading to
  an LLM via OpenRouter and stores the conversation in SQLite. RAG retrieval isn't wired in yet
  — the system prompt says so honestly — that's your next milestone per the PPT.

## Be upfront with your reviewer about the data

You only gave me 14 labelled rows (`data/wound_data.csv`). That is too few to train anything
stable, so `train_model.py`:

1. Fits a per-class Gaussian (mean + covariance) to your 14 rows and **samples synthetic rows**
   from it (clipped to plausible sensor ranges) — a documented small-data augmentation
   technique, not fabricated "real" data pretending to be real.
2. Has **no dataset at all** for days-to-heal, so it computes it from a transparent severity
   heuristic (see the big docstring/comments in `synthesize_healing_days`) — distance of each
   reading from a "healthy" centroid, mapped to a day range per condition, plus noise.

Both of these facts are printed in the terminal when you run the training script and saved to
`models/metadata.json`, and the dashboard's disclaimer footer says so too. When you get a real
longitudinal dataset (or your RAG-grounded estimate), you only need to redo this one script —
the rest of the app (`app.py`, templates) doesn't change.

## Setup

```bash
cd smart-bandage
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

# (models are already trained and committed under models/*.pkl,
#  but you can retrain any time with:)
python models/train_model.py

cp .env.example .env
# edit .env and paste your OpenRouter key into OPENROUTER_API_KEY
# (chat still works without a key -- it just tells you the key is missing
#  instead of calling the LLM, so you can demo login + prediction either way)

python app.py
```

Then open **http://127.0.0.1:5000**, sign up, and try the dashboard.

## Honest gaps to mention in your review (and what's next)

- **RAG isn't built yet.** The PPT's LangChain + FAISS + medical-literature-index layer is the
  next milestone — the chat's system prompt already says "no retrieval yet" so the demo doesn't
  overclaim.
- **No real ESP32/sensor hardware wired in.** Sliders stand in for live sensor streaming for
  this review; the `/api/predict` endpoint is the exact seam where real ESP32 JSON payloads
  would plug in later (same 5 features).
- **Days-to-heal is a heuristic, not a validated clinical estimate** — say this out loud to
  your guide, it's the most defensible way to present it.
- **classifier accuracy (~99%) is on a held-out split of the *synthetic* augmented data**, not
  real unseen patients — expect it to look far less clean once real data comes in, which is
  normal and worth noting proactively.
